# Director Brief: AWS学習ゲーム v4

このドキュメントは、実装担当(Codex GPT-5.5)へのプロデューサー/監督からの発注書である。
ターゲット読者は実装AI。要件と非要件をはっきり区別し、独自の設計判断は積極的に行ってよい。

## 0. ミッション

v3 (Cloud Sprint Architect) のプレイヤーから次のフィードバックを得た。

- ゲームクリアのモチベーションがわかない。各ラウンドのクリアだけが目的でつまらない。
- 選択肢が少なく、難易度が低い。知識の定着にも役立たない。

v4 はこの 2 点を構造的に解決する。コンセプトは最小限に引き継ぎ、ゲームとして作り直す。

## 1. 引き継ぐ核 (これだけは外さない)

- 案件 (要件文) を読んで AWS サービスを選ぶ
- 「なぜそのサービスが正解か」を短い解説で学べる
- 6 軸評価: 機能 / 可用性 / セキュリティ / 性能 / コスト / 運用負荷
- 日本語 UI、ダーク基調 (#0d1117 系) + 青系アクセント (#58a6ff 系)、軽い絵文字、ピュア HTML/CSS/JS (フレームワーク不要)

## 2. 解決すべき課題と方向性

### 2-1. メタな目的を作る (モチベ問題)

各ラウンドの正解収集だけでなく、**プレイ全体を貫く目的**を設計する。
以下のいずれか、または組み合わせを推奨する。最終判断は実装担当に任せる。

- **キャンペーン/キャリアモード**: 新人 → ジュニア → シニア → アーキテクトのように昇進する進行。章ごとにテーマ (ネットワーク章、データ層章、セキュリティ章、コスト最適化章 など)
- **持続するリソース**: 評判 (Reputation)、予算 (Budget)、信頼 (Trust)、SLA クレジット等。失敗で減り、成功で増える。一定値を切るとゲームオーバー、上限に達すると次章解放。
- **ボス案件 / マイルストーン**: 章末に複合要件のボス案件。複数の正解サービス組と複数のシナジーが要求される。
- **アンロック要素**: クリアした章でサービス・難易度・案件タイプが解放される。

メタ目的は「ただのスコア合計」ではなく、**プレイヤーの選択が将来のプレイ可能性に効く**こと。

### 2-2. 選択肢の量と質を増やす (難易度・定着問題)

v3 は 25 サービス・最大 3 選択・候補 8 個だった。v4 は次の方針で広げる。

- AWS サービスを **35〜45 種** まで拡張する。実在し、初学者〜中級者の語彙範囲。重要な追加候補:
  - Compute: EKS, Step Functions, SNS, Kinesis Data Streams, AppSync
  - Data: Aurora, Redshift, OpenSearch, Athena, Glue, EFS, FSx
  - Edge/Net: Direct Connect, Transit Gateway, Shield, Global Accelerator, NAT Gateway
  - Sec/Ops: GuardDuty, Security Hub, Config, Systems Manager, X-Ray, Organizations
- 案件 (チャレンジ) を **30件以上** 用意する。テーマと業種を散らす (EC, 動画配信, 製造IoT, 医療, 金融, ゲーム, BIなど)。
- 候補サービスは案件難易度に応じて **10〜16 枚** 表示。選択上限は案件ごとに変える (3〜6 枚)。
- 「**正解 (required)**」「**支援 (support / 加点)**」「**罠 (trap / 減点)**」「**互換不可 (conflict)**」をデータ化する。罠サービスは見た目もっともらしいが要件に合わないもの (例: コスト最優先の静的サイトに RDS Multi-AZ)。
- **シナジー** と **アンチパターン** を増やす。組み合わせで加点 / 減点。
- 知識定着のために **誤答した正解サービスを後の案件で再登場** させる「復習フラグ」を持つ (簡易スペースドリピティション)。

### 2-3. 案件タイプを増やす (定着問題)

すべて「ゼロから設計」だと退屈なので、ラウンドの **タイプを複数** 設ける。

- `design`: ゼロから構成を組む (現行)
- `incident`: 障害中の構成に対し、足すべきサービスを選ぶ
- `cost_cut`: 既存構成からコスト過剰な要素を抜く、または安価な代替を選ぶ
- `harden`: セキュリティ/コンプラ強化として追加するサービスを選ぶ
- `migrate`: オンプレ要件 → AWS サービスへの読み替え

タイプごとに UI ラベルを変え、評価軸の重み付けも変える。

## 3. 必須の機能要件

1. ルートは `game-v4/index.html`。`game-v4/css/`, `game-v4/js/`, `game-v4/docs/` に分割する。
2. ピュア HTML/CSS/JS のみ。npm 不要、ビルド不要、ローカル `file://` で開いて動く。外部 CDN・フォント不要。
3. モバイル幅 (375px) でも崩れずプレイできる。デスクトップ幅 (1280px) で気持ちよく見える。
4. メタ進行のセーブを `localStorage` で保持。タイトルから「続きから」「最初から」を選べる。
5. キーボードで提出 (Enter) と次へ (Enter / Space) ができる。マウスのみでもプレイ可。
6. 案件 30 件以上、サービス 35 種以上、シナジー 20 種以上を埋める。
7. ルートの `/index.html` (ハブページ) を更新し、v4 を「NEW」、v3 を「v3」ラベルに格下げしてリンクを追加する。レイアウトと既存リンク (v2, v1) は壊さない。
8. `game-v4/docs/spec.md` と `game-v4/docs/game-design.md` を v3 の体裁に倣って書き、メタ進行・案件タイプ・スコアリングを明確化する。

## 4. 非機能要件 / コード品質

- 可読性優先。1 ファイル 600 行を目安に分割。
- グローバル汚染を避け IIFE か `window.V4_*` 名前空間にまとめる。
- データ (services / challenges / synergies / chapters) は `js/data.js` に閉じる。
- ロジック (state / scoring / progression / save) は `js/game.js` か `js/progression.js` に分ける。
- 描画/イベントは `js/ui.js` に集約。DOM 文字列連結は最小限、`textContent` を基本に。
- 絵文字以外の装飾画像なし。アクセス可能なコントラストを確保。
- 過剰なコメントは書かない。意図が分かりにくい所のみ短く。
- v3 のコードを参考にしてよいが、リファクタしながら持ち込み、無駄な抽象化はしない。

## 5. デリバラブル

`game-v4/` 配下に動くゲーム一式と、以下のドキュメントを作る。

- `index.html`
- `css/style.css`
- `js/data.js`, `js/game.js`, `js/ui.js` (必要に応じて `js/progression.js` などを追加)
- `docs/spec.md`: 仕様書 (v3 spec.md の構造に倣う。コンセプト、課題分析、コアループ、評価、差別化マトリクスを含む)
- `docs/game-design.md`: ゲームデザイン書 (モード/章構成、サービス一覧、案件タイプ、スコアリング、UI ワイヤー、データ構造)
- ルートの `/index.html` を v4 リンク付きに更新

## 6. やってはいけないこと

- v1, v2, v3 のフォルダや既存ファイルを **書き換えない / 移動しない**
- 大量の Excel/CSV/Pickle ファイル (`*.xlsx`, `*.csv`, `*.pickle`) を読まない・触らない。ゲームと無関係。
- 外部ネットワーク取得 (CDN, fonts) を index.html に書かない。
- README.md を勝手に増やさない (`docs/` 配下のみ作成可)。
- 「とりあえず TODO」「未実装」「ダミーデータ」のような未完成箇所を残さない。

## 7. 受け入れ基準

- `game-v4/index.html` を直接ブラウザで開いて、タイトル → キャンペーン開始 → 章を 1 つクリア → メタ進行が反映される、まで通る
- 失敗ループ (評判低下でゲームオーバー的演出) もコードパスとして存在する
- 案件ごとに正解/罠/シナジーがロジックで効いており、解説と一致する
- root の `index.html` から v4 へ正しく遷移する
- README や他フォルダに破壊的変更がない (`git status` で v4 関連と root index.html のみ)

## 8. 進め方の推奨手順 (実装担当 = Codex 向け)

1. `game-v3/docs/spec.md` と `game-v3/docs/game-design.md` を読む (引き継ぐ核の確認)
2. `game-v3/js/data.js`, `game-v3/js/game.js`, `game-v3/js/ui.js`, `game-v3/css/style.css` をざっと読む (流用可能箇所の確認)
3. `game-v4/docs/spec.md` と `game-v4/docs/game-design.md` を **先に** 書く (設計を固める)
4. `js/data.js` でサービスと案件と章を入れる
5. `js/progression.js` (またはまとめて `js/game.js`) でメタ進行とセーブ
6. `js/game.js` でラウンドロジックとスコアリング
7. `js/ui.js` で画面遷移
8. `css/style.css` でビジュアル
9. `game-v4/index.html` で組み上げ
10. ルート `index.html` を更新
11. 各画面遷移を擬似プレイで頭の中で踏み、整合チェック

質問が必要な箇所があっても、本ブリーフ内で意思決定して進めること。判断のメモは `docs/` のドキュメントに残せばよい。
